1. Introduction au projet

webserv est un serveur HTTP/1.1 écrit en C++98, inspiré de NGINX. Le projet vous fait implémenter un serveur web capable de servir des fichiers statiques, gérer des uploads, exécuter des scripts CGI (Python, PHP), lister des dossiers, et bien plus.

📌 Ce que fait le projet :
  • Un seul fichier de configuration (type NGINX) définit un ou plusieurs serveurs virtuels
  • Une boucle d'événements avec un unique poll() gère toutes les connexions
  • Les requêtes HTTP sont parsées incrémentalement (state machine)
  • Les réponses sont construites et envoyées au fil de l'eau
  • Le CGI utilise fork() + execve() avec des pipe()
  • Une seule règle : ne jamais planter

2. Le Makefile et la compilation

⚙️ Règle absolue : pas de relink. Si vous lancez make deux fois de suite, la deuxième fois ne doit rien recompiler. 
CXX      = c++
CXXFLAGS = -Wall -Wextra -Werror -std=c++98 -MMD
NAME     = webserv

SRCS = main.cpp ConfigParser.cpp ServerConfig.cpp \
       Server.cpp HttpRequest.cpp HttpResponse.cpp
OBJS = $(SRCS:.cpp=.o)
DEPS = $(OBJS:.o=.d)

all: $(NAME)

$(NAME): $(OBJS)
	$(CXX) $(CXXFLAGS) -o $(NAME) $(OBJS)

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

clean:     rm -f $(OBJS) $(DEPS)
fclean:    clean ; rm -f $(NAME)
re:        fclean all

-include $(DEPS)
.PHONY: all clean fclean re

Ce qu'il faut comprendre

  • -MMD génère des fichiers .d qui listent les dépendances (headers). Si un .hpp change, le .cpp qui l'inclut est recompilé automatiquement
  • Le -include $(DEPS) importe ces dépendances
  • Pas de relink : la règle $(NAME): $(OBJS) ne fait rien si les .o sont à jour
  • make re = make fclean + make — reconstruction complète

❓ Quiz Makefile

Q1 : Quelle option du compilateur interdit l'utilisation de fonctionnalités C++11 ?
Réponse : -std=c++98. Sans cette option, vous pourriez utiliser auto, nullptr, etc. et avoir 0 à la correction.
Q2 : Que se passe-t-il si vous modifiez un fichier .hpp ?
Réponse : Grâce à -MMD, tous les .cpp qui #include ce .hpp sont recompilés automatiquement. Make lit les dépendances dans les fichiers .d générés.
Q3 : Comment vérifier qu'il n'y a pas de relink ?
Réponse : Lancez make deux fois. La deuxième doit afficher make: Nothing to be done for 'all' ou rien du tout. Si elle recompile, c'est 0.

3.3 Tokenization (analyse lexicale)

Le parseur ConfigParser fonctionne en deux phases :

  1. Tokenization : découpe le fichier en tokens
  2. Parsing : analyse la structure des tokens

Types de tokens :

3.4 Parsing (analyse syntaxique)

Le parsing suit une grammaire simple :

fichier   → server* EOF
server    → "server" "{" directive* "}"
directive → mot args? ";"
location  → "location" mot "{" directive* "}"
args      → mot+

Chaque directive est dispatchée vers un handler :

  • listen → parseListen() : extrait host:port
  • server_name → parseServerName()
  • client_max_body_size → parseClientMaxBodySize() : supporte les suffixes K/M/G
  • error_page → parseErrorPage()
  • root → handleRoot()
  • index → handleIndex()
  • methods → handleMethods() : remplace la liste par défaut
  • autoindex → handleAutoindex() : "on" ou "off"
  • upload_store → handleUploadStore()
  • cgi_ext → handleCgiExt()
  • return → handleReturn()

La méthode parseSize() convertit "1M" en 1048576 :

// ConfigParser.cpp (lignes 31-55)
size_t parseSize(const std::string& str) {
    std::string num;
    char suffix = 0;
    for (size_t i = 0; i < str.size(); ++i) {
        if (str[i] >= '0' && str[i] <= '9')
            num += str[i];
        else { suffix = str[i]; break; }
    }
    size_t value = std::atol(num.c_str());
    switch (suffix) {
        case 'K': value *= 1024; break;
        case 'M': value *= 1024 * 1024; break;
        case 'G': value *= 1024 * 1024 * 1024; break;
        case 0: break;
        default: error("Invalid size suffix");
    }
    return value;
}

3.5 Vérification : ports dupliqués

À la fin du parsing, checkDuplicatePorts() vérifie qu'aucun port n'est déclaré deux fois :

void ConfigParser::checkDuplicatePorts(const std::vector<ServerConfig>& configs) {
    std::set<int> ports;
    for (size_t i = 0; i < configs.size(); ++i) {
        int port = configs[i].port;
        if (ports.find(port) != ports.end()) {
            std::cerr << "Error: Duplicate port " << port << std::endl;
            exit(1);
        }
        ports.insert(port);
    }
}

❓ Quiz Configuration

Q1 : Que se passe-t-il si on déclare deux fois le même port dans la configuration ?
Réponse : Erreur fatale au démarrage. La méthode checkDuplicatePorts() détecte le doublon, affiche "Error: Duplicate port X" et appelle exit(1).
Q2 : Quelle est la différence entre nextToken() et peekToken() ?
Réponse : peekToken() renvoie le token courant sans avancer. nextToken() renvoie le token courant et avance d'un cran. C'est le principe du lookahead : on regarde le prochain token pour décider quoi faire.
Q3 : Si une directive inconnue apparaît dans un bloc server, que se passe-t-il ?
Réponse : Le parseur affiche "Error: Unknown directive 'truc'" et appelle exit(1). Le serveur ne démarre pas avec une configuration invalide. C'est une règle du sujet.
Q4 : Quelle est la taille maximale du body par défaut ?
Réponse : 1 048 576 octets = 1 Mo. Défini dans ServerConfig::ServerConfig() comme valeur de client_max_body_size.

4. Architecture générale

4.1 Le point d'entrée (main.cpp)

int main(int argc, char** argv) {
    ConfigParser parser;
    std::vector<ServerConfig> configs;

    if (argc >= 2)
        configs = parser.parse(argv[1]);
    else
        configs = parser.parseFromDefault();

    Server server(configs);
    server.run();
    return 0;
}

Le main est minimal :

  1. Crée un ConfigParser
  2. Parse le fichier de config (argument CLI ou conf/default.conf)
  3. Crée un Server avec les configurations
  4. Appelle server.run() qui ne revient jamais (boucle infinie)

❓ Quiz Architecture

Q1 : Quel conteneur fait le lien entre un fd et son client ?
Réponse : std::map<int, Client> clients_. La clé est le descripteur de fichier (socket), la valeur est la structure Client qui contient la requête, la réponse, la configuration associée, etc.
Q2 : Comment est associé un client à sa configuration serveur ?
Réponse : Dans handleAccept(), lors de l'acceptation d'une nouvelle connexion, le client reçoit un pointeur vers la configuration du socket d'écoute : client.config = &configs_[idx]. Si l'idx dans fds_ est 0, le client est associé à configs_[0].
Q3 : Pourquoi listen_count_ est-il stocké séparément ?
Réponse : Pour distinguer les sockets d'écoute (index < listen_count_) des sockets clients (index ≥ listen_count_) dans la boucle poll(). Quand un socket d'écoute a POLLIN, on accepte une connexion. Quand un client a POLLIN, on lit des données.

5. La boucle d'événements — le cœur du projet

🚨 RÈGLE ABSOLUE — 0 si non respectée :
  • Un seul poll() (ou select()/epoll()/kqueue()) dans tout le programme
  • Il surveille lecture ET écriture simultanément
  • Au maximum une lecture ou écriture par client par itération
  • Jamais de read()/write() sur socket sans passer par poll() d'abord
  • Ne jamais vérifier errno après read/recv/write/send
  • Le retour de read/recv doit vérifier les deux cas : -1 et 0
  • En cas d'erreur, le client est retiré immédiatement
  • Pas de fork() ailleurs que pour le CGI

5.1 Initialisation des sockets

void Server::setupListenSockets() {
    for (size_t i = 0; i < configs_.size(); ++i) {
        // 1. getaddrinfo() : résout host:port
        struct addrinfo hints, *res;
        std::memset(&hints, 0, sizeof(hints));
        hints.ai_family = AF_UNSPEC;      // IPv4 ou IPv6
        hints.ai_socktype = SOCK_STREAM;  // TCP
        hints.ai_flags = AI_PASSIVE;
        getaddrinfo(conf.host, port_str, &hints, &res);

        // 2. socket()
        int sock = socket(res->ai_family, res->ai_socktype, res->ai_protocol);

        // 3. SO_REUSEADDR := réutiliser l'adresse après redémarrage
        int opt = 1;
        setsockopt(sock, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

        // 4. bind()
        bind(sock, res->ai_addr, res->ai_addrlen);

        // 5. listen()
        listen(sock, SOMAXCONN);

        // 6. O_NONBLOCK obligatoire
        fcntl(sock, F_SETFL, O_NONBLOCK);

        // 7. Ajouter au tableau pollfd
        struct pollfd pfd;
        pfd.fd = sock;
        pfd.events = POLLIN;
        pfd.revents = 0;
        fds_.push_back(pfd);
    }
    listen_count_ = fds_.size();
}
💡 Pourquoi O_NONBLOCK ? Parce que accept(), read() et write() sur des sockets bloquants peuvent bloquer le serveur. Avec O_NONBLOCK et poll(), on est sûr de ne jamais bloquer. Tous les sockets doivent être non-bloquants.

5.2 La boucle principale (Server::run)

void Server::run() {
    while (true) {
        cleanupDeadFds();  // retire les fd marqués -1

        int ret = poll(&fds_[0], fds_.size(), -1);
        if (ret < 0) { std::cerr << "poll() failed"; break; }

        for (size_t i = 0; i < fds_.size(); ++i) {
            if (fds_[i].revents == 0) continue;

            if (i < listen_count_) {
                if (fds_[i].revents & POLLIN)
                    handleAccept(i);    // nouvelle connexion
            } else if (fds_[i].revents & POLLIN) {
                handleRead(i);          // données entrantes
            } else if (fds_[i].revents & POLLOUT) {
                handleWrite(i);         // socket prêt à écrire
            } else {
                closeClient(i);         // POLLHUP/ERR/NVAL
            }
        }
    }
}

5.3 Accept — handleAccept()

void Server::handleAccept(size_t idx) {
    struct sockaddr_in addr;
    socklen_t addrlen = sizeof(addr);
    int client_fd = accept(fds_[idx].fd, (struct sockaddr*)&addr, &addrlen);
    if (client_fd < 0) return;

    fcntl(client_fd, F_SETFL, O_NONBLOCK);  // NON-BLOCKING !

    Client client;
    client.fd = client_fd;
    client.response_sent = 0;
    client.reading_done = false;
    client.config = &configs_[idx];   // associe le client à sa config
    client.location = NULL;
    clients_[client_fd] = client;

    struct pollfd pfd;
    pfd.fd = client_fd;
    pfd.events = POLLIN;              // on commence par lire
    pfd.revents = 0;
    fds_.push_back(pfd);
}

5.4 Read — handleRead()

void Server::handleRead(size_t idx) {
    int fd = fds_[idx].fd;
    Client& client = clients_[fd];

    char buf[4096];
    ssize_t n = read(fd, buf, sizeof(buf));

    if (n <= 0) {     // ← vérifie à la fois -1 ET 0
        closeClient(idx);
        return;
    }

    client.request.feed(std::string(buf, n));

    if (client.request.isComplete()) {
        client.reading_done = true;
        processRequest(client);
        fds_[idx].events = POLLOUT;  // on veut maintenant écrire
    }
}
🔴 Point crucial de correction : la condition n <= 0 couvre les deux cas : -1 (erreur) et 0 (connexion fermée par le client). Ne faites PAS if (n == -1) sans vérifier 0. Ne vérifiez PAS errno.

5.5 Write — handleWrite()

void Server::handleWrite(size_t idx) {
    int fd = fds_[idx].fd;
    Client& client = clients_[fd];

    size_t remaining = client.response.size() - client.response_sent;
    ssize_t n = write(fd, client.response.c_str() + client.response_sent, remaining);

    if (n <= 0) {
        closeClient(idx);
        return;
    }

    client.response_sent += n;

    if (client.response_sent >= client.response.size())
        closeClient(idx);  // tout est envoyé
}

5.6 Fermeture — closeClient()

void Server::closeClient(size_t idx) {
    int fd = fds_[idx].fd;
    if (fd >= 0) {
        close(fd);
        clients_.erase(fd);
        fds_[idx].fd = -1;    // marqué pour suppression
        fds_[idx].events = 0;
    }
}

Les fd marqués à -1 sont nettoyés au début de la prochaine itération par cleanupDeadFds().

void Server::cleanupDeadFds() {
    for (size_t i = 0; i < fds_.size(); ) {
        if (fds_[i].fd == -1) {
            fds_.erase(fds_.begin() + i);
            if (i < listen_count_)
                listen_count_--;
        } else {
            ++i;
        }
    }
}

❓ Quiz Event Loop

Q1 : Pourquoi ne faut-il JAMAIS vérifier errno après read()/write() ?
Réponse : Parce que c'est une règle explicite du sujet. "Never check errno after read/recv/write/send." Si le correcteur voit errno dans votre code, c'est 0 à l'évaluation. De toute façon, vérifier n <= 0 suffit pour détecter les erreurs.
Q2 : Comment le serveur passe-t-il de la lecture à l'écriture pour un client ?
Réponse : Une fois que la requête est complète (client.request.isComplete()), le serveur appelle processRequest() pour construire la réponse, puis change les événements poll() du client : fds_[idx].events = POLLOUT. Au prochain tour de boucle, poll() indiquera que le client est prêt à recevoir les données.
Q3 : Que se passe-t-il si poll() indique POLLHUP sur un client ?
Réponse : Le else final (closeClient(i)) se déclenche. POLLHUP signifie que le client a fermé la connexion. La règle dit : "on any error, remove the client immediately".
Q4 : Pourquoi le tableau fds_ contient-il à la fois les sockets d'écoute et les clients ?
Réponse : Pour qu'un seul appel à poll() suffise à tout surveiller. C'est la règle du sujet : "Exactly one poll() in the entire program, in the main loop." Et il doit "monitor both read and write readiness simultaneously" — tous les fd sont dans le même tableau.

6. Le parseur de requêtes HTTP

6.1 Format d'une requête HTTP

GET /path/to/resource?query=string HTTP/1.1\r\n
Host: example.com\r\n
Content-Type: application/x-www-form-urlencoded\r\n
Content-Length: 27\r\n
\r\n
body...

Une requête HTTP a trois parties :

  1. Request Line : METHOD path HTTP/version\r\n
  2. Headers : paires nom: valeur\r\n
  3. Body : séparé par \r\n vide, taille définie par Content-Length ou Transfer-Encoding: chunked

6.2 La machine à états (State Machine)

enum State { REQUEST_LINE, HEADERS, BODY, COMPLETE };
enum ChunkState { CHUNK_SIZE, CHUNK_DATA };
données → [REQUEST_LINE] → \r\n → [HEADERS] → \r\n vide → [BODY] → ... → [COMPLETE] │ │ │ ┌──────┴──────┐ │ │ chunked? │ content-length? │ │ CHUNK_SIZE │ attend N bytes │ │ ↓ │ │ │ CHUNK_DATA │ │ │ ↓ │ │ │ (size = 0) │ │ │ COMPLETE │ │ └─────────────┘

6.3 La méthode feed()

bool HttpRequest::feed(const std::string& data) {
    buf_ += data;

    while (state_ != COMPLETE) {
        if (state_ == REQUEST_LINE || state_ == HEADERS) {
            size_t pos = buf_.find("\r\n");
            if (pos == std::string::npos) break;  // pas encore de ligne complète

            std::string line = buf_.substr(0, pos);
            buf_.erase(0, pos + 2);  // retire la ligne + \r\n

            if (state_ == REQUEST_LINE) {
                parseRequestLine(line);
                state_ = HEADERS;
            } else if (line.empty()) {
                state_ = BODY;       // fin des headers
            } else {
                parseHeaderLine(line);
            }
        }

        if (state_ == BODY) {
            if (chunked_) {
                // voir section 6.5
            } else if (content_length_ > 0) {
                if (buf_.size() < content_length_) break;
                body = buf_.substr(0, content_length_);
                buf_.erase(0, content_length_);
                state_ = COMPLETE;
            } else {
                state_ = COMPLETE;  // pas de body
            }
        }
    }
    return state_ == COMPLETE;
}

6.4 Parsing de la request line

void HttpRequest::parseRequestLine(const std::string& line) {
    std::istringstream iss(line);
    iss >> method >> path >> http_version;

    size_t qpos = path.find('?');
    if (qpos != std::string::npos) {
        query_string = path.substr(qpos + 1);
        path = path.substr(0, qpos);
    }
}

GET /search?q=hello HTTP/1.1 donne :

  • method = "GET"
  • path = "/search"
  • query_string = "q=hello"
  • http_version = "HTTP/1.1"

6.5 Parsing des headers

void HttpRequest::parseHeaderLine(const std::string& line) {
    size_t colon = line.find(':');
    if (colon == std::string::npos) return;

    std::string key = line.substr(0, colon);
    std::string value = line.substr(colon + 1);

    // trim leading spaces
    size_t start = value.find_first_not_of(" \t");
    if (start != std::string::npos) value = value.substr(start);

    // lower-case header key pour comparaison insensible à la casse
    for (size_t i = 0; i < key.size(); ++i)
        key[i] = std::tolower(static_cast<unsigned char>(key[i]));

    headers[key] = value;

    if (key == "content-length")
        content_length_ = std::atol(value.c_str());
    else if (key == "transfer-encoding" && value.find("chunked") != std::string::npos)
        chunked_ = true;
}
🎯 Pourquoi lower-case ? HTTP/1.1 spécifie que les noms d'en-têtes sont insensibles à la casse (Content-Type = content-type = CONTENT-TYPE). En les convertissant tous en minuscules, on simplifie la comparaison.

6.6 Le chunked encoding

Le transfert chunked permet d'envoyer un body sans connaître sa taille à l'avance :

POST /cgi HTTP/1.1\r\n
Transfer-Encoding: chunked\r\n
\r\n
7\r\n                ← taille du premier chunk (hexadécimal)
Mozilla\r\n         ← données du chunk
9\r\n                ← taille du second chunk
Developer\r\n       ← données
0\r\n                ← chunk de taille 0 = fin
\r\n                 ← trailer optionnel

Le code qui déchunk (lignes 52-87 de HttpRequest.cpp) utilise une sous-state machine :

if (chunk_state_ == CHUNK_SIZE) {
    // lire la ligne de taille (en hexa)
    size_t pos = buf_.find("\r\n");
    if (pos == std::string::npos) break;

    std::string size_line = buf_.substr(0, pos);
    buf_.erase(0, pos + 2);

    long raw = std::strtol(size_line.c_str(), NULL, 16);
    if (raw < 0) { state_ = COMPLETE; break; }  // erreur
    chunk_remaining_ = static_cast<size_t>(raw);

    if (chunk_remaining_ == 0) {
        // dernier chunk : ignorer jusqu'au \r\n final
        size_t tpos = buf_.find("\r\n");
        if (tpos == std::string::npos) break;
        buf_.erase(0, tpos + 2);
        state_ = COMPLETE;
        break;
    }
    chunk_state_ = CHUNK_DATA;
}

if (chunk_state_ == CHUNK_DATA) {
    if (buf_.size() < chunk_remaining_ + 2) break;
    body += buf_.substr(0, chunk_remaining_);
    buf_.erase(0, chunk_remaining_ + 2);  // retire le \r\n suivant
    chunk_state_ = CHUNK_SIZE;
}
Pourquoi le sujet exige le déchunking ? Le CGI attend un body complet via stdin, terminé par EOF. Si on envoyait les chunks bruts au CGI, il ne pourrait pas les interpréter. Il faut donc reconstituer le body avant de le passer au CGI.

❓ Quiz HTTP Parsing

Q1 : Pourquoi la méthode feed() peut-elle recevoir la requête en plusieurs fois ?
Réponse : Parce que TCP est un protocole stream. Les données peuvent arriver en morceaux. La boucle poll() déclenche handleRead() à chaque fois que des données sont disponibles, et feed() les accumule dans buf_. Le parsing se fait incrémentalement : on traite ce qu'on peut et on attend le reste au prochain appel.
Q2 : Comment détecte-t-on la fin des headers ?
Réponse : Une ligne vide (\r\n seul) dans l'état HEADERS. Le code vérifie : si la ligne lue est vide (line.empty()), on passe à l'état BODY. C'est le signal standard HTTP/1.1 pour séparer les headers du body.
Q3 : Que fait-on si aucun Content-Length ni Transfer-Encoding: chunked n'est présent ?
Réponse : On considère qu'il n'y a pas de body. Après les headers, on passe immédiatement à l'état COMPLETE. C'est le cas par exemple des requêtes GET et DELETE.
Q4 : Dans le chunked encoding, en quelle base est écrite la taille de chaque chunk ?
Réponse : En hexadécimal (base 16). Le code utilise std::strtol(size_line.c_str(), NULL, 16) pour convertir. Le chunk "7" en hexa = 7 octets, "A" = 10, "1F" = 31, etc.

❓ Quiz Réponses HTTP

Q1 : Quand le serveur renvoie-t-il un 201 Created ?
Réponse : Quand un fichier a été uploadé avec succès via POST. Le body de la réponse contient le chemin du fichier créé.
Q2 : Quelle est la différence entre 403 et 404 ?
Réponse : 403 Forbidden = la ressource existe mais on n'a pas le droit d'y accéder (pas de permission, dossier sans index et autoindex off). 404 Not Found = la ressource n'existe pas (stat() échoue, ou aucune location ne matche).
Q3 : Le serveur renvoie-t-il Connection: keep-alive ou close ?
Réponse : Connection: close par défaut. Après l'envoi de la réponse, la connexion est fermée (closeClient() est appelé). Le keep-alive n'est pas implémenté.

8. Les méthodes HTTP

8.1 Le routing — processRequest()

void Server::processRequest(Client& client) {
    // 1. Mélanger le chemin avec les locations
    client.location = matchLocation(path, client.config);
    if (!client.location) { buildErrorResponse(client, 404); return; }

    // 2. Vérifier que la méthode est gérée (GET/POST/DELETE seulement)
    if (method != "GET" && method != "POST" && method != "DELETE") {
        buildErrorResponse(client, 501); return;
    }

    // 3. Vérifier que la méthode est autorisée par la location
    if (location->methods.find(method) == location->methods.end()) {
        buildErrorResponse(client, 405); return;
    }

    // 4. Vérifier la taille du body
    if (client.request.body.size() > client.config->client_max_body_size) {
        buildErrorResponse(client, 413); return;
    }

    // 5. Vérifier si c'est une requête CGI
    bool is_cgi = checkCgiExtension(client.request.path, client.location);
    
    // 6. Déléguer au bon handler
    if (is_cgi)          handleCGI(client);
    else if (method == "GET")    handleGet(client);
    else if (method == "POST")   handlePost(client);
    else if (method == "DELETE") handleDelete(client);
}

8.2 matchLocation() — le plus long préfixe

const LocationConfig* Server::matchLocation(
    const std::string& path, const ServerConfig* config) const {

    const LocationConfig* best = NULL;
    size_t best_len = 0;

    for (size_t i = 0; i < config->locations.size(); ++i) {
        const LocationConfig& loc = config->locations[i];
        if (path.compare(0, loc.path.size(), loc.path) == 0) {
            if (loc.path.size() > best_len) {
                best = &loc;
                best_len = loc.path.size();
            }
        }
    }
    return best;
}

Exemple : une requête sur /kapouet/pouic/toto avec deux locations :

  • /kapouet → match (6 caractères) ✓ (plus spécifique)
  • / → match (1 caractère) ✓

Résultat : la location /kapouet est choisie car son préfixe est plus long.

8.3 resolvePath() — du chemin URL au chemin fichier

std::string Server::resolvePath(const Client& client) const {
    std::string subpath;
    if (client.location->path == "/") {
        subpath = client.request.path;
    } else {
        subpath = client.request.path.substr(client.location->path.size());
    }
    if (subpath.empty()) subpath = "/";
    return client.location->root + subpath;
}

Exemple : requête /cgi-bin/test.py, location /cgi-bin avec root ./cgi-bin :

  • subpath = /test.py (on enlève le préfixe /cgi-bin)
  • fullpath = ./cgi-bin/test.py

8.4 GET — fichier statique

void Server::handleGet(Client& client) {
    std::string fullpath = resolvePath(client);

    struct stat st;
    if (stat(fullpath.c_str(), &st) < 0) {
        buildErrorResponse(client, 404);  // fichier inexistant
        return;
    }

    if (S_ISDIR(st.st_mode))
        serveDirectory(client, fullpath);  // dossier → index/autoindex
    else if (S_ISREG(st.st_mode))
        serveFile(client, fullpath);       // fichier → lu et envoyé
    else
        buildErrorResponse(client, 403);   // ni fichier ni dossier
}

8.5 POST — upload de fichier

void Server::handlePost(Client& client) {
    const std::string& upload_store = client.location->upload_store;

    if (!upload_store.empty()) {
        // Générer un nom de fichier unique : timestamp_taille
        std::ostringstream filename;
        filename << time(NULL) << "_" << client.request.body.size();

        std::string filepath = upload_store + "/" + filename.str();
        int fd = open(filepath.c_str(), O_WRONLY | O_CREAT | O_EXCL, 0644);
        if (fd < 0) { buildErrorResponse(client, 500); return; }

        ssize_t written = write(fd, client.request.body.c_str(),
                                client.request.body.size());
        close(fd);

        if (written < 0 || static_cast<size_t>(written) != client.request.body.size()) {
            unlink(filepath.c_str());
            buildErrorResponse(client, 500);
            return;
        }

        // Réponse 201 Created
        HttpResponse resp;
        resp.setStatus(201);
        resp.setBody("<h1>201 Created</h1><p>File: " + filepath + "</p>");
        client.response = resp.toString();
    } else {
        // Pas d'upload_store : juste accuser réception
        HttpResponse resp;
        resp.setStatus(200);
        resp.setBody("<h1>POST " + client.request.path + "</h1>"
                     "<p>Body size: " + body.size() + "</p>");
        client.response = resp.toString();
    }
}

8.6 DELETE — suppression de fichier

void Server::handleDelete(Client& client) {
    std::string fullpath = resolvePath(client);

    struct stat st;
    if (stat(fullpath.c_str(), &st) < 0) {
        buildErrorResponse(client, 404); return;
    }

    if (S_ISDIR(st.st_mode)) {
        buildErrorResponse(client, 403); return;  // pas de suppression de dossier
    }

    if (unlink(fullpath.c_str()) < 0) {
        buildErrorResponse(client, 403); return;
    }

    HttpResponse resp;
    resp.setStatus(204);           // No Content
    resp.setBody("");
    client.response = resp.toString();
}

8.7 Directory listing (autoindex)

void Server::serveDirectory(Client& client, const std::string& path) {
    // 1. Essayer le fichier index
    std::string index_path = path + "/" + client.location->index;
    struct stat st;
    if (stat(index_path.c_str(), &st) == 0 && S_ISREG(st.st_mode)) {
        serveFile(client, index_path);
        return;
    }
    // 2. Pas d'index → autoindex ou 403
    if (client.location->autoindex)
        serveDirectoryListing(client, path);
    else
        buildErrorResponse(client, 403);
}

serveDirectoryListing() utilise opendir() + readdir() :

void Server::serveDirectoryListing(Client& client, const std::string& path) {
    DIR* dir = opendir(path.c_str());
    if (!dir) { buildErrorResponse(client, 403); return; }

    std::ostringstream html;
    html << "<html><head><title>Index of "
         << client.request.path << "</title></head><body>"
         << "<h1>Index of " << client.request.path << "</h1><hr><ul>";

    struct dirent* entry;
    while ((entry = readdir(dir)) != NULL) {
        std::string name(entry->d_name);
        if (name == ".") continue;
        html << "<li><a href=\"" << name << "\">" << name << "</a></li>";
    }
    html << "</ul><hr></body></html>";
    closedir(dir);

    HttpResponse resp;
    resp.setStatus(200);
    resp.setContentType("text/html");
    resp.setBody(html.str());
    client.response = resp.toString();
}

❓ Quiz Méthodes HTTP

Q1 : Si une requête PUT arrive, que se passe-t-il ?
Réponse : Le code vérifie method != "GET" && method != "POST" && method != "DELETE", ce qui est vrai pour PUT → réponse 501 Not Implemented. Le serveur ne crash jamais.
Q2 : Quand une location interdit POST mais que le client envoie un POST ?
Réponse : La vérification location->methods.find("POST") échoue → réponse 405 Method Not Allowed. Les méthodes autorisées par défaut sont GET, POST, DELETE sauf si la config les redéfinit.
Q3 : Que renvoie DELETE sur un dossier ?
Réponse : 403 Forbidden. Le code vérifie S_ISDIR(st.st_mode) et refuse la suppression d'un dossier (on ne supprime que des fichiers avec unlink()).
Q4 : Quel est l'algorithme de matching des locations ?
Réponse : Le plus long préfixe (longest prefix match). On parcourt toutes les locations, on garde celle dont le path correspond au début de l'URL ET a la plus grande longueur. Ainsi, /cgi-bin est préféré à / pour une requête sur /cgi-bin/test.py.

9. Le CGI

📘 Rappel : CGI = Common Gateway Interface. Permet d'exécuter un script (Python, PHP, binaire) pour générer une réponse HTTP. Le serveur envoie les données via stdin et récupère le résultat via stdout.

9.1 Le pipeline CGI

Serveur (fork) │ ├─ pipe(stdin_pipe) ──── parent écrit, enfant lit ├─ pipe(stdout_pipe) ──── enfant écrit, parent lit │ └─ fork() │ ├── [ENFANT] │ ├─ dup2(stdin_pipe[0], STDIN_FILENO) │ ├─ dup2(stdout_pipe[1], STDOUT_FILENO) │ ├─ ferme les 4 extrémités de pipe inutilisées │ ├─ construit le tableau d'environnement │ ├─ execve("/usr/bin/python3", [script_path], envp) │ ├─ si échec : execve(script_path, [script_path], envp) │ └─ si échec : exit(1) │ └── [PARENT] ├─ ferme stdin_pipe[0] et stdout_pipe[1] ├─ write(stdin_pipe[1], request.body) ├─ close(stdin_pipe[1]) → EOF pour le CGI ├─ read(stdout_pipe[0]) → boucle jusqu'à EOF ├─ close(stdout_pipe[0]) ├─ waitpid(pid) → attend la fin du processus └─ parse la sortie du CGI (headers + body)

9.2 Le code complet

void Server::handleCGI(Client& client) {
    std::string script_path = resolvePath(client);

    // 1. Créer les pipes
    int stdin_pipe[2], stdout_pipe[2];
    if (pipe(stdin_pipe) < 0 || pipe(stdout_pipe) < 0) {
        buildErrorResponse(client, 500); return;
    }

    // 2. fork()
    pid_t pid = fork();
    if (pid < 0) {
        close(stdin_pipe[0]); close(stdin_pipe[1]);
        close(stdout_pipe[0]); close(stdout_pipe[1]);
        buildErrorResponse(client, 500); return;
    }

    if (pid == 0) {  // ── ENFANT ──
        dup2(stdin_pipe[0], STDIN_FILENO);
        dup2(stdout_pipe[1], STDOUT_FILENO);
        close(stdin_pipe[0]);  close(stdin_pipe[1]);
        close(stdout_pipe[0]); close(stdout_pipe[1]);

        // 3. Construire l'environnement
        std::vector<std::string> env_strings;
        env_strings.push_back("REQUEST_METHOD=" + client.request.method);
        env_strings.push_back("QUERY_STRING=" + client.request.query_string);

        std::ostringstream ps; ps << client.config->port;
        env_strings.push_back("SERVER_PORT=" + ps.str());

        std::string sn = client.config->server_name;
        if (sn.empty()) sn = "localhost";
        env_strings.push_back("SERVER_NAME=" + sn);
        env_strings.push_back("SERVER_PROTOCOL=" + client.request.http_version);

        std::ostringstream cl;
        cl << client.request.body.size();
        env_strings.push_back("CONTENT_LENGTH=" + cl.str());

        // CONTENT_TYPE
        std::map<std::string,std::string>::const_iterator hit;
        hit = client.request.headers.find("content-type");
        if (hit != client.request.headers.end())
            env_strings.push_back("CONTENT_TYPE=" + hit->second);

        // SCRIPT_NAME, PATH_INFO, PATH_TRANSLATED
        env_strings.push_back("SCRIPT_NAME=" + client.request.path);
        env_strings.push_back("PATH_INFO=");
        env_strings.push_back("PATH_TRANSLATED=" + script_path);

        // HTTP_* headers
        for (const auto& hdr : { "host", "user-agent", "accept" }) {
            hit = client.request.headers.find(hdr);
            if (hit != client.request.headers.end()) {
                std::string key = std::string("HTTP_") + hdr;
                std::transform(hdr, ...); // "host" → "HTTP_HOST"
                env_strings.push_back(key + "=" + hit->second);
            }
        }

        // Convertir en char**
        std::vector<char*> envp;
        for (size_t i = 0; i < env_strings.size(); ++i)
            envp.push_back(const_cast<char*>(env_strings[i].c_str()));
        envp.push_back(NULL);

        // 4. execve — d'abord avec Python, puis direct
        char* argv[3];
        argv[0] = const_cast<char*>("/usr/bin/python3");
        argv[1] = const_cast<char*>(script_path.c_str());
        argv[2] = NULL;
        execve(argv[0], argv, &envp[0]);

        argv[0] = const_cast<char*>(script_path.c_str());
        execve(argv[0], argv, &envp[0]);

        exit(1);  // si execve échoue
    }

    // ── PARENT ──
    close(stdin_pipe[0]);
    close(stdout_pipe[1]);

    // 5. Envoyer le body au CGI (via stdin)
    if (!client.request.body.empty())
        write(stdin_pipe[1], client.request.body.c_str(), client.request.body.size());
    close(stdin_pipe[1]);  // EOF → le CGI comprend la fin

    // 6. Lire la sortie du CGI (lecture bloquante = OK pour les pipes)
    std::string cgi_output;
    char buf[4096];
    ssize_t n;
    while ((n = read(stdout_pipe[0], buf, sizeof(buf))) > 0)
        cgi_output.append(buf, n);
    close(stdout_pipe[0]);

    // 7. Attendre la fin du processus
    int status;
    waitpid(pid, &status, 0);

    // 8. Parser la sortie du CGI
    HttpResponse resp;
    resp.setStatus(200);

    size_t header_end = std::string::npos;
    size_t sep_len = 0;
    size_t pos_rnrn = cgi_output.find("\r\n\r\n");
    size_t pos_nn  = cgi_output.find("\n\n");

    if (pos_rnrn != std::string::npos) {
        header_end = pos_rnrn; sep_len = 4;
    } else if (pos_nn != std::string::npos) {
        header_end = pos_nn; sep_len = 2;
    }

    if (header_end != std::string::npos) {
        std::string header_section = cgi_output.substr(0, header_end);
        resp.setBody(cgi_output.substr(header_end + sep_len));

        // Parse les headers CGI
        std::istringstream hss(header_section);
        std::string hline;
        while (std::getline(hss, hline)) {
            if (!hline.empty() && hline[hline.size()-1] == '\r')
                hline.erase(hline.size()-1);
            size_t colon = hline.find(':');
            if (colon != std::string::npos) {
                std::string key = hline.substr(0, colon);
                std::string val = hline.substr(colon + 1);
                // trim
                size_t start = val.find_first_not_of(" \t");
                if (start != std::string::npos) val = val.substr(start);

                if (key == "Content-Type" || key == "content-type")
                    resp.setContentType(val);
                else if (key == "Location" || key == "location") {
                    resp.setStatus(302);
                    resp.setHeader("Location", val);
                } else if (key == "Status" || key == "status") {
                    int sc; std::istringstream(val) >> sc;
                    resp.setStatus(sc);
                }
            }
        }
    } else {
        resp.setBody(cgi_output);  // pas de headers
    }
    client.response = resp.toString();
}

❓ Quiz CGI

Q1 : Quel appel système est utilisé pour créer le processus CGI ?
Réponse : fork(). C'est le seul endroit du programme où fork() est autorisé (et obligatoire pour le sujet).
Q2 : Comment le CGI sait-il que le body est terminé ?
Réponse : Par EOF (End of File). Le parent ferme le pipe stdin du CGI après avoir écrit tout le body : close(stdin_pipe[1]). Quand le CGI lit sur stdin, read() renvoie 0 à la fin, ce qui signifie "fin des données".
Q3 : Pourquoi la lecture du stdout du CGI est-elle bloquante (read en boucle) ?
Réponse : Parce que le sujet dit qu'on n'est pas obligé d'utiliser poll() pour les pipes ou les fichiers disques. "You are not required to use poll() for regular disk files" — les pipes sont aussi exemptés. On peut donc faire un read() bloquant sur le pipe.
Q4 : Que se passe-t-il si le script CGI n'existe pas ?
Réponse : Le processus enfant appelle execve() qui échoue deux fois, puis exit(1). Le parent reçoit un code de sortie non-nul via waitpid(), mais ne le vérifie pas → réponse 200 avec un body vide. C'est une simplification délibérée (ponytail: ne pas compliquer).
Q5 : Pourquoi les headers HTTP sont-ils préfixés par HTTP_ dans l'environnement CGI ?
Réponse : C'est la spécification CGI/1.1 (RFC 3875). Les variables d'environnement CGI suivent un format standard : les headers HTTP sont convertis en majuscules, préfixés par HTTP_, et les tirets deviennent des underscores. Exemple : User-Agent → HTTP_USER_AGENT.

10.3 Gestion des connexions

closeClient() est appelé dans plusieurs cas :

  • read() retourne ≤ 0 → client fermé
  • write() retourne ≤ 0 → client fermé
  • Réponse complètement envoyée → client fermé
  • poll() indique POLLHUP/POLLERR/POLLNVAL → client fermé
void Server::closeClient(size_t idx) {
    int fd = fds_[idx].fd;
    if (fd >= 0) {
        close(fd);
        clients_.erase(fd);
        fds_[idx].fd = -1;    // marqué pour nettoyage
        fds_[idx].events = 0;
    }
}

Le nettoyage des fd marqués se fait au début de run() avec cleanupDeadFds().

🔴 Correction : Ne JAMAIS vérifier errno après read()/write(). Ne JAMAIS faire de read()/write() sans être passé par poll(). Vérifier n <= 0 couvre les deux cas : -1 (erreur) et 0 (EOF).

❓ Quiz Erreurs

Q1 : Si une requête arrive sur un chemin qu'aucune location ne matche, quel code est renvoyé ?
Réponse : 404 Not Found. La méthode matchLocation() retourne NULL si aucun préfixe ne correspond.
Q2 : Dans quel ordre sont vérifiés les codes d'erreur dans processRequest() ?
Réponse : (1) 404 si pas de location, (2) 501 si méthode inconnue, (3) 405 si méthode non autorisée, (4) 413 si body trop gros. Ensuite on délegue au handler.
Q3 : Que fait le serveur si read() renvoie 0 ?
Réponse : Il appelle closeClient(idx). Un retour de 0 signifie que le client a fermé la connexion (EOF).

BONUS : Simulation de correction

Voici des questions typiques que les correcteurs 42 posent pendant l'évaluation. Essayez d'y répondre sans regarder le code, puis vérifiez.

❓ Question 1 — La règle d'or

"Montrez-moi où se trouve votre appel à poll(). Un seul ? Quels fd surveille-t-il ?"
L'appel est dans Server::run() à la ligne 105 de Server.cpp : poll(&fds_[0], fds_.size(), -1). Il surveille tous les fd : les sockets d'écoute (en lecture) et les sockets clients (en lecture ou écriture). C'est le seul appel poll() dans tout le programme.

❓ Question 2 — errno

"Où vérifiez-vous errno après read() ou write() ?"
Nulle part. C'est interdit par le sujet. Notre code vérifie n <= 0 pour détecter les erreurs. La valeur de retour suffit.

❓ Question 3 — La transition lecture → écriture

"Comment passez-vous de la lecture à l'écriture pour un client ? Montrez le code."
Dans handleRead(), quand client.request.isComplete() est vrai, on appelle processRequest(client) pour remplir client.response, puis on change les événements : fds_[idx].events = POLLOUT. Le prochain poll() nous dira quand on peut écrire.

❓ Question 4 — La vérification body

"Où et comment vérifiez-vous la limite de taille du body ?"
Dans processRequest() : if (client.request.body.size() > client.config->client_max_body_size) → 413 Payload Too Large. La taille max est configurable via client_max_body_size (défaut 1M).

❓ Question 5 — La gestion de non-blocking

"Vos sockets sont-ils tous en non-blocking ? Montrez où vous le faites."
Oui. Dans setupListenSockets() pour les sockets d'écoute : fcntl(sock, F_SETFL, O_NONBLOCK). Dans handleAccept() pour les clients : fcntl(client_fd, F_SETFL, O_NONBLOCK).

❓ Question 6 — Le chunked encoding

"Où se fait le déchunking ? Expliquez le principe."
Dans HttpRequest::feed() aux lignes 52-87. On a une sous-state machine avec CHUNK_SIZE (on lit la taille hexadécimale) et CHUNK_DATA (on lit les données). Le dernier chunk de taille 0 marque la fin. Le body complet est reconstitué dans body — le CGI reçoit les données brutes, pas les chunks.

❓ Question 7 — Le matching de location

"Si j'ai / et /cgi-bin, quelle location matche pour /cgi-bin/test.py ?"
/cgi-bin, car c'est le plus long préfixe qui correspond. L'algorithme parcourt toutes les locations et garde celle dont loc.path est un préfixe et a la plus grande longueur.

❓ Question 8 — Les codes de statut

"Citez-moi 5 codes de statut gérés par votre serveur et dites quand ils sont utilisés."
200 (GET réussi), 201 (upload créé), 204 (DELETE réussi), 301/302 (redirection), 400 (bad request), 403 (forbidden), 404 (not found), 405 (method not allowed), 413 (body trop gros), 500 (erreur interne), 501 (méthode inconnue), 505 (HTTP version).

❓ Question 9 — Le fork()

"Où se trouve votre fork() ? Pouvez-vous en avoir ailleurs ?"
Dans handleCGI(), ligne 512 de Server.cpp. C'est le seul fork() du programme. Le sujet spécifie : "fork() is only allowed for CGI — nothing else."

❓ Question 10 — La boucle infinie en CGI

"Que se passe-t-il si un script CGI boucle à l'infini ?"
Actuellement, le serveur bloque dans la boucle read() du parent (ligne 597). C'est un problème connu : on devrait idéalement ajouter un timeout avec alarm() ou un pipe non-bloquant. Néanmoins, le serveur ne crash pas — il bloque.
